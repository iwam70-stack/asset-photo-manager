## 2. 用語

| 用語 | 定義 |
| --- | --- |
| 備品 | 本アプリで写真を記録する管理対象物 |
| 備品シール | 備品番号が記載され、備品に貼付されたシール |
| 備品番号 | 実物の備品シールにある「物品番号」欄の値を本アプリで呼ぶ名称。`NN-NNNNNN`形式で表し、運用上、一つの備品を一意に識別する文字列。数字2桁、ASCIIハイフン、数字6桁で構成し、先頭ゼロを保持する |
| シール写真 | 備品番号を読み取るために撮影した備品シールの写真 |
| 全体写真 | 備品番号確定後に撮影する備品全体の写真 |
| OCR | シール写真に含まれる文字を認識する処理 |
| 備品番号候補 | OCR結果から備品番号として利用者へ提示する文字列 |
| 撮影ジョブ | 1件の備品について、確定した備品番号、シール写真、全体写真、および処理状態をひとまとまりとして扱う管理単位 |
| 完成済みジョブ | 備品番号が確定し、シール写真、全体写真、および復旧に必要な情報が端末内へ保存された撮影ジョブ |
| 未完成ジョブ | 完成済みジョブの条件を満たしていない撮影ジョブ |
| 未送信ジョブ | Google Driveへの保存が完了していない撮影ジョブ |
| アップロードキュー | Google Driveへの保存を待つ完成済みジョブの集合 |
| 送信済み | 必要な写真がGoogle Driveへ保存されたことを確認できた状態 |

## 3. 目的

### 3.1 解決したい問題

備品シールから備品番号を読み取り、シール写真と備品全体写真を対応付けて記録し、
通信状況に左右されず撮影作業を継続できるようにする。

撮影済みデータをGoogle Driveへ保存し、備品番号と写真の対応関係を維持する。

### 3.2 想定利用者

初期利用者は備品管理担当者1人とし、本人だけがアプリを使用する。
初期利用端末は備品管理担当者の私物スマートフォン1台とするBYOD運用とし、その端末では本人に割り当てられた通常の業務用Google Workspaceアカウントを使用する。アプリ専用または備品管理専用のWorkspaceアカウントは新設しない。

初期運用で問題がないことを確認した後、同じGoogle Workspaceドメインの業務用アカウントを持つ備品配置先の職員へ展開する可能性がある。その場合も各職員本人に割り当てられた業務用Workspaceアカウントを使用し、単一のWorkspaceアカウントを複数人で共用しない。ただし、将来の利用人数、端末数、権限、同時利用、および運用手順は未確定とし、将来の可能性だけを理由に利用者管理や複数利用者向け機能を先行実装しない。

### 3.3 対象範囲

- 備品シールの撮影
- OCRによる文字認識と備品番号候補の抽出
- 利用者によるOCR結果の確認および手修正
- 備品番号確定後の備品全体写真の撮影
- 備品番号、シール写真、および全体写真の一組での管理
- 撮影データの端末内保存
- 未送信データの保持と復旧
- Google認証
- Google Driveへの保存
- 送信失敗時の再送

### 3.4 対象外

- 備品台帳そのものの作成、編集、および検索
- 備品の貸出、返却、棚卸し結果などの業務管理
- Google Drive以外のクラウドサービスへの保存
- iOSを初期開発の優先対象とすること
- 複数利用者または複数端末による同時利用
- 利用者間の役割分担、アプリ内の利用者管理、および管理者権限と一般利用者権限の区分
- 同時編集を前提とした排他制御
- 利用者別の撮影履歴または監査履歴
- 備品配置先職員向けの専用機能
- アプリ独自の遠隔削除、担当変更時の未送信データ移行、および端末故障・紛失時の未送信写真復元

対象外の範囲を将来追加するかどうかは、この初期版では決定しない。

## 4. 基本業務フロー

1. 利用者がアプリを起動する。
2. アプリが完成済みの未送信ジョブを復旧する。
3. 利用者が備品シールを撮影する。
4. アプリがOCRを実行し、備品番号候補を抽出する。
5. 利用者が候補を確認し、必要に応じて手修正する。
6. 利用者が備品番号を確定する。
7. 利用者が備品全体を撮影する。
8. アプリが備品番号、シール写真、および全体写真を1件の撮影ジョブとして端末内へ保存する。
9. 同じ備品番号の未送信または送信失敗の完成済みジョブが端末内にある場合、新しいジョブの保存完了後に旧ジョブを置き換える。
10. アプリが完成済みジョブをアップロードキューへ登録する。
11. 利用者が「未送信写真を送信」操作を行う。
12. アプリが操作時点の完成済み未送信ジョブをすべて今回の送信対象として確定し、Google認証と通信状態を確認してGoogle Driveへ保存する。操作後に完成したジョブは今回の送信対象へ追加せず、次回の送信操作の対象とする。
13. 保存に失敗したジョブは、再送可能な状態で端末内に保持する。

## 5. 機能要件

### 5.1 アプリ起動・状態復旧

#### FR-001 アプリ起動時の未送信ジョブ復旧

- 要件：アプリは、起動時に端末内へ保存されている完成済みの未送信ジョブを復旧しなければならない。
- 完了条件：アプリを終了して再起動した後も、終了前に保存済みだった完成済みの未送信ジョブを確認でき、送信対象として扱える。
- 状態：確定
- 備考：未完成ジョブをどこまで復旧するかは未確定とする。

### 5.2 シール写真撮影

#### FR-010 シール写真の撮影

- 要件：利用者は、備品番号を読み取る対象となる備品シールを撮影できなければならない。
- 完了条件：利用者が撮影操作を行い、OCRの対象となるシール写真を確認できる。
- 状態：確定
- 備考：シール写真と全体写真に共通する形式、解像度、および圧縮率はQ-014に従う。具体的なカメラまたは画像処理APIは未確定とする。

### 5.3 OCR

#### FR-020 シール写真のOCR実行

- 要件：アプリは、撮影したシール写真に対してOCRを実行しなければならない。
- 完了条件：シール写真の撮影後、認識された文字列または認識できなかったことを確認できる。
- 状態：確定
- 備考：認識精度および処理時間の目標値は未確定とする。

### 5.4 備品番号候補抽出

#### FR-030 備品番号候補の抽出

- 要件：アプリは、OCR結果を正規化した後にハイフンを含む`NN-NNNNNN`形式として認識できた値、または値全体が8桁の数字だけの場合に2桁目の後へASCIIハイフンを補った値を有効候補とし、重複を除いてちょうど1件の場合だけ利用者へ提示しなければならない。
- 完了条件：全角数字を半角数字へ、一般的なハイフン類似文字をASCIIハイフンへ正規化し、ハイフン前後の空白を除去する。正規化後の値が8桁の数字だけに一致する場合は2桁目の後へASCIIハイフンを補い、`^[0-9]{2}-[0-9]{6}$`で検証できる。同一の正規化済み文字列を1件として扱い、有効候補が1件の場合だけ2桁欄と6桁欄へ表示する。0件または複数件の場合は候補を表示せず、読み取り失敗として扱う。7桁以下、9桁以上、または周辺文字を含む値から数字を選択せず、バーコード下などの数字列を優先する推測も行わない。
- 状態：確定
- 備考：備品番号の3文字目は運用上必ずハイフンであるため、正規化後の値全体が8桁の数字だけである場合に限って補完する。先頭ゼロを保持する文字列として扱う。複数の8桁数字からの選択、候補の順位付け、ラベルとの距離による推測、および候補一覧の表示は行わない。

### 5.5 OCR結果の確認・手修正

#### FR-040 OCR結果の確認と手修正

- 要件：利用者は、前半2桁と後半6桁の数字を別々の入力欄で確認・訂正できなければならず、ハイフンを入力しない。有効候補が0件または複数件の場合、アプリは読み取れなかった旨を表示し、両方の入力欄を空欄にして数字入力を促さなければならない。
- 完了条件：2桁欄と6桁欄の間に固定表示されたハイフンを確認でき、各欄で先頭ゼロを保持して数字を入力できる。OCR候補を反映した場合も、利用者の確認操作なしに自動確定されない。有効候補が0件または複数件の場合は不確かなOCR結果が入力欄へ反映されず、空欄から入力できる。
- 状態：確定
- 備考：画面構成と表示内容はQ-020に従う。色、フォント、余白、およびFlutterウィジェットの具体的な選択は実装時に設計する。

### 5.6 備品番号確定

#### FR-050 備品番号の確定

- 要件：アプリは、利用者の確認を経た前半2桁と後半6桁をASCIIハイフンで連結し、`NN-NNNNNN`形式の文字列として備品番号を確定できなければならない。
- 完了条件：前半が2桁、後半が6桁そろった場合だけ確定でき、利用者の確定操作後に先頭ゼロを保持した備品番号が対象の撮影ジョブへ対応付けられる。
- 状態：確定
- 備考：入力検証は`NN-NNNNNN`形式（正規表現`^[0-9]{2}-[0-9]{6}$`）を前提とし、各数字列の先頭ゼロを保持する。画面構成はQ-020に従い、Flutterウィジェットの具体的な選択は実装時に設計する。

### 5.7 全体写真撮影

#### FR-060 備品全体写真の撮影

- 要件：利用者は、備品番号の確定後に、その備品の全体写真を撮影できなければならない。
- 完了条件：備品番号が確定している撮影手順で、全体写真用ガイドフレームと確定済み備品番号を確認し、備品全体が枠内に収まるよう撮影できる。撮影後に写真と備品番号を確認し、撮り直すか保存へ進むかを選択できる。
- 状態：確定
- 備考：ガイドフレームは撮影位置を案内するだけとし、枠への完全一致を要求せず、枠外を自動的に切り抜かない。はみ出しによって撮影を禁止せず、写真の縦横比を維持して撮影後の確認は利用者が行う。具体的な寸法、縦横比、色、線種、および透明度は実機UI設計時に調整する。再撮影時の上書きはFR-072で管理する。

### 5.8 撮影ジョブ管理

#### FR-070 写真と備品番号の一組での管理

- 要件：アプリは、1件の備品について、確定した備品番号、シール写真、および全体写真を1件の撮影ジョブとして管理しなければならない。
- 完了条件：異なる備品の写真が混在せず、対象の備品番号から同じジョブに属する2枚の写真を識別できる。
- 状態：確定
- 備考：備品番号は運用上、一つの備品を一意に識別し、備品番号ごとに有効な完成済み撮影ジョブは1件だけとする。再撮影時の処理はFR-072で管理する。

#### FR-071 撮影ジョブの完成判定

- 要件：アプリは、備品番号が確定し、シール写真、全体写真、および復旧に必要な情報が端末内へ保存された場合に限り、撮影ジョブを完成済みとして扱わなければならない。
- 完了条件：いずれかの条件を満たさないジョブは完成済みまたはアップロード対象として扱われず、すべての条件を満たすジョブだけが完成済みになる。
- 状態：確定
- 備考：未完成ジョブはプロセス終了、異常終了、または端末再起動後に復旧せず、未送信キューへ登録しない。一時的なバックグラウンド移行でプロセスと画面状態が残る場合は、直ちに破棄する必要はない。

#### FR-072 再撮影時の端末内ジョブ置き換え

- 要件：アプリは、同じ備品番号で新しい撮影ジョブが完成した場合、端末内にある未送信または送信失敗の旧ジョブを新しいジョブで置き換え、備品番号ごとに有効な未送信ジョブを1件だけとしなければならない。新しいジョブが完成するまでは旧ジョブを維持し、再撮影の中断または保存失敗によって旧ジョブを失ってはならない。
- 完了条件：新しいジョブの端末内保存後、新しい2枚の写真が送信対象として有効になり、旧ジョブが有効な未送信ジョブとして併存しない。再撮影を途中で中断または保存に失敗した場合は旧ジョブが維持される。送信済み写真がDriveにある場合は、既存ファイルを変更せず、再撮影した2枚を同名の新規ファイルとして保存できる。
- 状態：確定
- 備考：アプリ内では履歴、別名、別ジョブ、および世代を管理しない。Drive上に過去の同名ファイルが残ることは許容し、その整理はアプリの責務としない。送信競合の実装方式および一部送信成功時の処理は、この要件では定めない。

### 5.9 端末内保存

#### FR-080 アップロード前の端末内保存

- 要件：アプリは、シール写真と全体写真を縦横比を維持した長辺最大1920px、JPEG品質85のJPEG（MIMEタイプ`image/jpeg`、拡張子`.jpg`）へ調整し、Google Driveへアップロードする前に、調整後の画像をキャッシュ領域ではないアプリ専用内部ストレージへ永続保存しなければならない。元画像の長辺が1920pxを超える場合だけ長辺1920pxへ縮小し、1920px以下の場合は拡大してはならない。写真を端末のギャラリーまたは共有メディア領域へ保存してはならない。
- 完了条件：シール写真と全体写真の両方に同じ設定が適用され、縦向き・横向きを問わず縦横比が維持される。通信できない状態でも調整後の画像を含む完成済みジョブが失われず、アプリ再起動後に未送信ジョブとして確認できる。保存した写真は一般的なギャラリーアプリから閲覧できず、利用者はアプリ内の確認画面で確認できる。
- 状態：確定
- 備考：端末内で未送信写真として永続保存するのは調整後画像だけとし、元画像と調整後画像の両方を業務データとして永続保存しない。完成済みジョブ情報はSQLiteへ保存し、Flutterからの操作には`sqflite`を使用する。具体的な画像処理API、ディレクトリ名、ファイルパス、SQLiteの物理スキーマ、およびマイグレーションは実装時に設計する。

### 5.10 アップロードキュー

#### FR-090 完成済みジョブのキュー登録

- 要件：アプリは、撮影ジョブが完成して端末内保存に成功した時点ではGoogle Driveへの送信を自動開始せず、完成済みの未送信ジョブをアップロードキューへ登録しなければならない。利用者が「未送信写真を送信」操作を行った時点で、完成済みかつ未送信のジョブを個別選択させずすべて今回の送信対象として確定しなければならない。
- 完了条件：ジョブ完成だけでは送信が開始されず、完成済みジョブがアップロードキューへ登録され、未完成ジョブがキューおよび送信対象に含まれない。「未送信写真を送信」操作時点の完成済み未送信ジョブがすべて今回の送信対象となり、操作後に完成したジョブは開始済みの送信対象へ追加されず次回の送信操作の対象となる。
- 状態：確定
- 備考：同じ備品番号の未送信または送信失敗の旧ジョブは、新しい完成済みジョブで送信対象ごと置き換える。「未送信写真を送信」の配置と画面構成はQ-020に従う。送信対象の処理順序、同時実行数、および送信競合の具体的な制御方法は未確定とする。

#### FR-091 オフライン時の未送信データ保持

- 要件：アプリは、オフライン、送信待ち、または送信失敗の場合、未送信ジョブと写真を固定の日数上限を設けず、正常な送信完了まで端末内に保持しなければならない。アプリ終了、端末再起動、端末紛失、担当変更、または時間経過だけを理由に自動削除してはならない。
- 完了条件：送信が正常に完了していないジョブと写真が、時間経過、アプリ終了、端末再起動、またはネットワーク復旧後も送信対象として残り、ネットワーク復旧だけでは送信が開始されず、利用者の「未送信写真を送信」操作によって送信を開始できる。
- 状態：確定
- 備考：オフラインからオンラインへ変化したことだけを契機とした自動送信は行わない。アプリのアンインストール、アプリデータ消去、または端末初期化後の保持は保証せず、端末故障・紛失時のバックアップまたは復元は行わない。利用者が未送信ジョブを手動削除できるかは未確定とする。

#### FR-092 撮影処理とアップロード処理の独立

- 要件：利用者は、撮影済みデータのアップロード完了を待たずに次の備品の撮影へ進めなければならない。
- 完了条件：完成済みジョブが未送信または送信中であっても、アップロード開始または完了を待たずに次の備品についてシール写真の撮影を開始できる。
- 状態：確定
- 備考：アップロード処理の実現方式はこの文書では定めない。

### 5.11 Google認証

#### FR-100 Google Drive利用時の認証

- 要件：利用者本人は、スマートフォン上で本人の業務用Google Workspaceアカウントへサインインしなければならない。アプリはGoogleアカウントへのサインインとGoogle Driveへのアクセス許可を分離して扱い、Drive操作に必要なアクセス許可をOAuth 2.0による認可として必要な操作の段階で取得できなければならない。
- 完了条件：本人の業務用WorkspaceアカウントへのサインインとDriveアクセスの認可を個別に確認でき、必要な認証および認可が成立している場合だけアップロードを実行できる。成立していない場合は送信成功として扱われない。
- 状態：確定
- 備考：アプリはGoogleアカウントのパスワードを保持しない。認証および認可はスマートフォン上で行い、独自の認証バックエンド、サービスアカウント、およびサービスアカウント秘密鍵を使用しない。認証には`google_sign_in`を使用し、送信操作時に`https://www.googleapis.com/auth/drive.file`スコープを要求する。トークンの取得・保存・更新方法の詳細は、採用パッケージの仕様に従って実装時に決定する。

### 5.12 Google Driveへの保存

#### FR-110 Google Driveへの写真保存

- 要件：アプリは、完成済みジョブに属するシール写真と全体写真について、縦横比を維持した長辺最大1920px、JPEG品質85へ調整して端末内へ永続保存したJPEG（MIMEタイプ`image/jpeg`、拡張子`.jpg`）を、正規形の備品番号を用いた`<備品番号>_label.jpg`と`<備品番号>_overall.jpg`の名前で、所属職員が利用できる既存のGoogle Workspace共有ドライブ内に設けた備品管理用フォルダへ新規ファイルとしてアップロードしなければならない。担当者個人のマイドライブは保存先として使用せず、保存されたファイルは共有ドライブに属するものとする。
- 完了条件：本人の業務用Workspaceアカウントに設定された既存の権限で、対象ジョブの必要な写真が所定の共有ドライブ内フォルダへ保存されたことを確認した後に限り、そのジョブが送信済みになる。書き込めない場合は保存成功として扱わず、利用者へエラーを案内する。
- 状態：確定
- 備考：送信ごとに2枚を新規作成し、同名ファイルが存在しても検索、特定、内容更新、削除、移動、整理、統合、共有設定変更、および権限変更を行わない。撮影日時、内部ID、連番、世代などの識別情報をファイル名へ追加しない。新規アップロードで得たDriveファイルIDを、過去ファイル更新用の対応情報として送信完了後も保持しない。Drive API v3の`files.create`で、ビルド時設定として注入した所定フォルダのIDを親に指定し、共有ドライブ対応のため`supportsAllDrives`を有効にする。実際のフォルダIDをソースコード、文書、テストコード、およびGit履歴へ含めない。初期版では保存先選択・変更画面を設けない。送信競合の制御は未確定とする。一部送信時はFR-120に従う。

### 5.13 再送

#### FR-120 送信失敗後の再送

- 要件：アプリは、利用者が「未送信写真を送信」操作で開始した一つの送信処理の中だけで、再試行可能な一時的エラーに対して自動再送しなければならない。対象は、一時的な通信切断、タイムアウト、Drive APIの`429 Too Many Requests`、`500`、`502`、`503`、`504`、およびDrive APIから再試行可能と判断できるレート制限エラーとする。片方だけのDrive保存に成功した場合もジョブ全体を送信未完了とし、自動再送および次回の利用者操作では2枚とも新規アップロードしなければならない。
- 完了条件：再試行可能なエラーでは、初回送信後に最大3回、1秒、2秒、4秒を基準として各回に0～1秒のランダム時間を加えて自動再送し、初回を含む最大4回で終了する。成功しなかったジョブと写真は削除せず端末内に保持し、利用者が再度「未送信写真を送信」操作を行ったとき、その時点のほかの完成済み未送信ジョブと一括して新しい送信処理の対象となる。利用者による操作回数には上限を設けない。
- 状態：確定
- 備考：Google認証が必要な状態、Driveアクセス認可の拒否・取消し、保存先への書き込み権限不足、リクエストまたは保存先設定の不備、容量などの上限超過、その他再試行しても解消が見込めないエラー、および再試行可能か判断できないエラーは自動再送しない。専用の再送ボタン、写真単位の選択・状態・再送、および成功済み写真のDriveファイルIDを用いた再送制御は設けない。自動再送回数は実行中の送信処理だけで管理し、永続保存せず、次回の利用者操作では0回から開始する。

#### FR-121 バックグラウンド移行時の保持と送信結果表示

- 要件：初期版ではバックグラウンド送信を行わず、送信処理はアプリが画面に表示されている間に実行しなければならない。送信対象の全ジョブについて正常な送信完了を確認した場合は、利用者が完了を明確に認識できるよう結果を表示し、一部でも送信できなかった場合は単に「送信完了」と表示せず、送信処理の終了と未送信データが残っていることを表示しなければならない。
- 完了条件：送信中にアプリ内で次の備品の撮影へ進んでも送信処理を進め、送信結果が表示される。アプリがバックグラウンドへ移った後に正常な送信完了を確認できなかったジョブを送信済みとして扱わず、ジョブと写真を保持し、アプリへ戻った後の「未送信写真を送信」操作で送信対象にできる。
- 状態：確定
- 備考：送信結果表示はアプリ終了後も閲覧できる履歴として永続保存しない。初期版では送信済み履歴画面、過去ジョブ一覧、送信済み件数の履歴、および過去のエラー閲覧機能を設けない。バックグラウンド移行時の即時停止、進行中の個別リクエストの扱い、および使用ライブラリは未確定とする。表示形式、配置、文言、および表示終了条件はQ-020、送信状態の名称と粒度はQ-024で管理する。

### 5.14 ローカルデータ管理

#### FR-130 送信状態の保持

- 要件：アプリは、完成済みジョブの送信状態をジョブ単位の`未送信`、`送信中`、`送信失敗`、`送信後処理中`の4状態で永続管理しなければならない。`送信完了`は一時的な結果表示とし、永続状態として保持してはならない。
- 完了条件：ジョブ完成時は`未送信`、送信開始時は`送信中`、1枚以上の失敗または完了未確認時は`送信失敗`、2枚のDrive保存確認後は`送信後処理中`となる。`送信後処理中`ではDriveへ再送せず、写真削除と必要な後処理の完了後にローカルジョブが削除される。
- 状態：確定
- 備考：起動時は`未送信`を未送信キューへ、`送信失敗`を再送対象へ復旧する。残存する`送信中`は正常完了未確認のため`送信失敗`へ変更して利用者操作を待ち、`送信後処理中`はDriveへ再送せず後処理だけを再開する。写真単位、エラー原因別、再送回数別には細分化せず、未完成ジョブの撮影進行状態も含めない。

#### FR-131 送信後のローカルデータ処理

- 要件：アプリは、撮影ジョブに属する必要な写真すべてがGoogle Driveへ正常に保存されたことを確認した後、対応するローカルのシール写真と全体写真を即時削除しなければならない。写真削除、そのジョブを未送信または送信失敗として復旧する必要がないことの確認、および必要なローカル後処理が正常に完了した後、備品番号、内部ジョブID、撮影日時、送信日時、送信状態、送信回数、最終エラー、Driveへ送信したファイル名、ローカル写真への参照、DriveファイルID、その他そのジョブだけに属するローカルメタデータも削除し、履歴として保持してはならない。
- 完了条件：ジョブ全体の正常な送信完了前は両写真と復旧に必要なジョブ情報が保持される。正常な送信、ローカル写真削除、および必要な後処理の完了後は、そのジョブの写真とジョブ固有情報が端末内に残らず、削除済みファイルの参照による異常が発生せず、削除済みジョブが未送信ジョブとして復旧しない。
- 状態：確定
- 備考：送信開始、送信途中、送信失敗、一部送信、または正常完了を確認できない状態では、両写真とジョブ情報を削除しない。2枚のDrive保存確認後は状態を`送信後処理中`へ更新してから端末内に残る写真と必要な後処理だけを実行する。写真削除に失敗した場合は残存写真を削除未完了データとして保持し、必要な写真すべての削除と後処理が完了するまでジョブ固有情報を削除しない。すでに削除された写真を復元しない。送信済み写真の確認先はGoogle Driveとする。Google認証情報とOAuthトークン、保存先フォルダなどのアプリ設定、アプリ全体の設定値、およびQ-019で管理する障害ログはジョブ履歴とは別であり、この削除対象に含めない。写真削除の順序、再試行回数、待ち時間、および利用者向け表示は未確定とする。

## 6. 異常時・中断時の要件

### 6.1 アプリ異常終了

- 完成済みの未送信ジョブは、アプリの異常終了後も失われてはならない。
- 送信処理中に終了したジョブは、送信成功を確認できない限り送信済みとして扱ってはならない。
- 未完成ジョブは復旧せず、次回起動時は新しい備品のシール撮影から開始する。復旧確認画面は設けない。

### 6.2 端末再起動

- 完成済みの未送信ジョブは、端末再起動後も復旧できなければならない。
- 再起動前に`送信中`だったジョブは`送信失敗`へ変更して自動送信せず、`送信後処理中`だったジョブはDriveへ再送せず残りの後処理だけを行わなければならない。

### 6.3 ネットワーク切断

- ネットワーク切断によって未送信ジョブおよび写真が失われてはならない。
- 通信できない間は未送信状態を維持し、再送可能でなければならない。

### 6.4 Google認証エラー

- 認証できない場合、アップロードを成功として扱ってはならない。
- 認証エラーが発生しても、撮影済みデータを保持しなければならない。
- 利用者が必要な対応を判断できるエラーを示さなければならない。

### 6.5 Google Drive APIエラー

- Google Driveへの保存結果を確認できない場合、対象ジョブを無条件に送信済みとして扱ってはならない。
- 送信に失敗したデータは削除せず、再送可能な状態で保持しなければならない。
- 一部の写真だけが保存された場合はジョブ全体を送信失敗として扱い、両写真とジョブ情報を保持し、再送時に2枚とも新規アップロードしなければならない。

### 6.6 カメラまたはOCRの失敗

- カメラによる撮影が完了しなかった場合、その写真を撮影済みとして扱ってはならない。
- OCRで候補を得られなかった場合、利用者が失敗を確認できなければならない。
- 有効候補が0件または複数件の場合は、読み取れなかった旨を表示し、2桁欄と6桁欄を空欄にして利用者へ数字入力を促さなければならない。

### 6.7 端末内保存失敗

- 必要な撮影データの端末内保存に失敗した場合、対象ジョブを完成済みとして扱ってはならない。
- 利用者が保存失敗と必要な対応を確認できなければならない。

## 8. データ要件

### 8.1 撮影ジョブ

- 1件の撮影ジョブは、1件の備品に関するデータを表さなければならない。
- 備品番号は、数字2桁、ASCIIハイフン、数字6桁からなる`NN-NNNNNN`形式の文字列として保持し、各数字列の先頭ゼロを失ってはならない。
- 備品番号は運用上、一つの備品を一意に識別し、異なる備品に同じ備品番号が割り当てられるケースは扱わない。
- 撮影ジョブは、確定した備品番号、シール写真、全体写真、および処理状態の対応関係を保持しなければならない。
- 撮影ジョブは、ファイル名だけに依存せず識別できなければならない。
- 内部的な識別子の形式は未確定とする。

### 8.2 シール写真

- シール写真は、対象の撮影ジョブと対応付けられなければならない。
- OCRに使用した写真を、アップロード前にアプリ専用内部ストレージへ保存し、ジョブ全体の正常な送信完了まで保持しなければならない。
- 保存形式はJPEG（MIMEタイプ`image/jpeg`、拡張子`.jpg`）とし、縦横比を維持した長辺最大1920px、JPEG品質85とする。長辺が1920pxを超える場合だけ1920pxへ縮小し、1920px以下の場合は拡大しない。実際の備品シールを正面、斜め、薄暗い場所、反射がある状態で撮影した場合、および小さいシールや傷・汚れ・かすれがあるシールについて、各文字がOCRに必要な大きさで写り、OCR可能であることを実機で検証する。

### 8.3 全体写真

- 全体写真は、備品番号確定後に撮影され、対象の撮影ジョブと対応付けられなければならない。
- 全体写真を、アップロード前にアプリ専用内部ストレージへ保存し、ジョブ全体の正常な送信完了まで保持しなければならない。
- 保存形式はJPEG（MIMEタイプ`image/jpeg`、拡張子`.jpg`）とし、シール写真と同じく縦横比を維持した長辺最大1920px、JPEG品質85とする。長辺が1920pxを超える場合だけ1920pxへ縮小し、1920px以下の場合は拡大しない。備品の種類と状態を業務上必要な範囲で、スマートフォンおよび一般的なPC画面から目視確認できることを実機で検証する。

### 8.4 送信状態

- 撮影ジョブごとに、Google Driveへの送信結果を識別できる情報を保持しなければならない。
- 送信成功が確認されていないジョブを送信済みとして記録してはならない。
- 送信失敗後に再送対象であることを識別できなければならない。
- 永続状態はジョブ単位の`未送信`、`送信中`、`送信失敗`、`送信後処理中`とし、一部送信は`送信失敗`、2枚のDrive保存確認後は`送信後処理中`として扱わなければならない。

## 9. 権限要件

- アプリは、シール写真および全体写真を撮影するために必要なカメラ利用権限を、利用者の許可に基づいて使用しなければならない。
- カメラ利用権限が許可されていない場合、撮影を成功として扱ってはならない。
- アプリは、Google Driveへの保存に必要な権限を、認証したGoogleアカウントから取得しなければならない。
- Google Driveの権限が不足している場合、アップロードを成功として扱ってはならない。
- アプリは、Google Workspaceおよび共有ドライブ側で設定された既存の権限を利用し、利用者登録、利用者名簿、役割・権限管理、利用者ごとの個別共有、共有設定変更、および権限変更を行ってはならない。
- 端末内保存に追加の利用者権限が必要かどうかは、対応Androidバージョンと保存対象の決定後に確認する。
- Google Driveで要求する具体的な権限の範囲は未確定とする。

## 10. 制約

- アプリはFlutterおよびDartで開発する。
- 初期開発ではAndroidを優先する。
- Androidの最低対応バージョンはAndroid 7.0（API 24）とし、`minSdk`は24とする。API 23以下は対応対象に含めない。
- `targetSdk`および`compileSdk`の具体的な値は未確定とする。
- 撮影データのクラウド保存先にはGoogle Driveを使用する。
- 保存先は既存のGoogle Workspace共有ドライブ内に設けた備品管理用フォルダとし、担当者個人のマイドライブを使用しない。
- 初期の備品管理担当者と将来利用する同一所属の職員をアプリ上の異なる役割として扱わず、利用資格とアクセス権限には既存のWorkspaceおよび共有ドライブの設定を使用する。
- 撮影処理とアップロード処理は、利用者がアップロード完了を待たず次の撮影へ進めるよう分離する。
- 撮影データは、Google Driveへアップロードする前に端末内へ保存する。
- GoogleアカウントへのサインインとGoogle Driveへのアクセス許可を分離し、Drive操作に必要なアクセス許可はOAuth 2.0による認可として取得する。
- 認証およびDriveアクセスの認可はスマートフォン上で行い、独自の認証バックエンドを設けない。
- Googleアカウントのパスワード、サービスアカウント、およびサービスアカウント秘密鍵をアプリで使用または保持しない。
- 状態管理方式、ローカル永続データの管理方式、および使用ライブラリは、この文書では決定しない。
