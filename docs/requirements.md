## 2. 用語

| 用語 | 定義 |
| --- | --- |
| 備品 | 本アプリで写真を記録する管理対象物 |
| 備品シール | 備品番号が記載され、備品に貼付されたシール |
| 備品番号 | 実物の備品シールにある「物品番号」欄の値を本アプリで呼ぶ名称。`NN-NNNNNN`形式で表し、運用上、一つの備品を一意に識別する文字列。数字2桁、ASCIIハイフン、数字6桁で構成し、先頭ゼロを保持する |
| シール写真 | 備品番号を読み取るために撮影した備品シールの写真 |
| 全体写真 | 備品番号確定後に撮影する備品全体の写真 |
| OCR | シール写真に含まれる文字を認識する処理 |
| 備品番号候補 | OCR結果から備品番号として利用者へ提示する文字列 |
| 撮影ジョブ | 1件の備品について、確定した備品番号、シール写真、全体写真、および処理状態をひとまとまりとして扱う管理単位 |
| 完成済みジョブ | 備品番号が確定し、シール写真、全体写真、および復旧に必要な情報が端末内へ保存された撮影ジョブ |
| 未完成ジョブ | 完成済みジョブの条件を満たしていない撮影ジョブ |
| 未送信ジョブ | Google Driveへの保存が完了していない撮影ジョブ |
| アップロードキュー | Google Driveへの保存を待つ完成済みジョブの集合 |
| 送信済み | 必要な写真がGoogle Driveへ保存されたことを確認できた状態 |

## 3. 目的

### 3.1 解決したい問題

備品シールから備品番号を読み取り、シール写真と備品全体写真を対応付けて記録し、
通信状況に左右されず撮影作業を継続できるようにする。

撮影済みデータをGoogle Driveへ保存し、備品番号と写真の対応関係を維持する。

### 3.2 想定利用者

初期利用者は備品管理担当者1人とし、本人だけがアプリを使用する。
初期利用端末は備品管理担当者の私物スマートフォン1台とするBYOD運用とし、その端末では本人に割り当てられた通常の業務用Google Workspaceアカウントを使用する。アプリ専用または備品管理専用のWorkspaceアカウントは新設しない。

初期運用で問題がないことを確認した後、同じGoogle Workspaceドメインの業務用アカウントを持つ備品配置先の職員へ展開する可能性がある。その場合も各職員本人に割り当てられた業務用Workspaceアカウントを使用し、単一のWorkspaceアカウントを複数人で共用しない。ただし、将来の利用人数、端末数、権限、同時利用、および運用手順は未確定とし、将来の可能性だけを理由に利用者管理や複数利用者向け機能を先行実装しない。

### 3.3 対象範囲

- 備品シールの撮影
- OCRによる文字認識と備品番号候補の抽出
- 利用者によるOCR結果の確認および手修正
- 備品番号確定後の備品全体写真の撮影
- 備品番号、シール写真、および全体写真の一組での管理
- 撮影データの端末内保存
- 未送信データの保持と復旧
- Google認証
- Google Driveへの保存
- 送信失敗時の再送

### 3.4 対象外

- 備品台帳そのものの作成、編集、および検索
- 備品の貸出、返却、棚卸し結果などの業務管理
- Google Drive以外のクラウドサービスへの保存
- iOSを初期開発の優先対象とすること
- 複数利用者または複数端末による同時利用
- 利用者間の役割分担、アプリ内の利用者管理、および管理者権限と一般利用者権限の区分
- 同時編集を前提とした排他制御
- 利用者別の撮影履歴または監査履歴
- 備品配置先職員向けの専用機能
- アプリ独自の遠隔削除、担当変更時の未送信データ移行、および端末故障・紛失時の未送信写真復元

対象外の範囲を将来追加するかどうかは、この初期版では決定しない。

## 4. 基本業務フロー

1. 利用者がアプリを起動する。
2. アプリが完成済みの未送信ジョブを復旧する。
3. 利用者が備品シールを撮影する。
4. アプリがOCRを実行し、備品番号候補を抽出する。
5. 利用者が候補を確認し、必要に応じて手修正する。
6. 利用者が備品番号を確定する。
7. 利用者が備品全体を撮影する。
8. アプリが備品番号、シール写真、および全体写真を1件の撮影ジョブとして端末内へ保存する。
9. 同じ備品番号の未送信または送信失敗の完成済みジョブが端末内にある場合、新しいジョブの保存完了後に旧ジョブを置き換える。
10. アプリが完成済みジョブをアップロードキューへ登録する。
11. 利用者が「未送信写真を送信」操作を行う。
12. アプリが操作時点の完成済み未送信ジョブをすべて今回の送信対象として確定し、Google認証と通信状態を確認してGoogle Driveへ保存する。操作後に完成したジョブは今回の送信対象へ追加せず、次回の送信操作の対象とする。
13. 保存に失敗したジョブは、再送可能な状態で端末内に保持する。

## 5. 機能要件

### 5.1 アプリ起動・状態復旧

#### FR-001 アプリ起動時の未送信ジョブ復旧

- 要件：アプリは、起動時に端末内へ保存されている完成済みの未送信ジョブを復旧しなければならない。
- 完了条件：アプリを終了して再起動した後も、終了前に保存済みだった完成済みの未送信ジョブを確認でき、送信対象として扱える。
- 状態：確定
- 備考：未完成ジョブをどこまで復旧するかは未確定とする。

### 5.2 シール写真撮影

#### FR-010 シール写真の撮影

- 要件：利用者は、備品番号を読み取る対象となる備品シールを撮影できなければならない。
- 完了条件：利用者が撮影操作を行い、OCRの対象となるシール写真を確認できる。
- 状態：確定
- 備考：写真の形式、解像度、および圧縮率は未確定とする。

### 5.3 OCR

#### FR-020 シール写真のOCR実行

- 要件：アプリは、撮影したシール写真に対してOCRを実行しなければならない。
- 完了条件：シール写真の撮影後、認識された文字列または認識できなかったことを確認できる。
- 状態：確定
- 備考：認識精度および処理時間の目標値は未確定とする。

### 5.4 備品番号候補抽出

#### FR-030 備品番号候補の抽出

- 要件：アプリは、OCR結果を正規化した後にハイフンを含む`NN-NNNNNN`形式として認識できた値だけを有効候補とし、重複を除いてちょうど1件の場合だけ利用者へ提示しなければならない。
- 完了条件：全角数字を半角数字へ、一般的なハイフン類似文字をASCIIハイフンへ正規化し、ハイフン前後の空白を除去した結果を`^[0-9]{2}-[0-9]{6}$`で検証できる。同一の正規化済み文字列を1件として扱い、有効候補が1件の場合だけ2桁欄と6桁欄へ表示する。0件または複数件の場合は候補を表示せず、読み取り失敗として扱う。ハイフンなしの8桁数字から候補を生成せず、バーコード下などの数字列を備品番号候補として推測しない。
- 状態：確定
- 備考：先頭ゼロを保持する文字列として扱う。候補の順位付け、8桁数字の選択、ラベルとの距離による推測、および候補一覧の表示は行わない。

### 5.5 OCR結果の確認・手修正

#### FR-040 OCR結果の確認と手修正

- 要件：利用者は、前半2桁と後半6桁の数字を別々の入力欄で確認・訂正できなければならず、ハイフンを入力しない。有効候補が0件または複数件の場合、アプリは読み取れなかった旨を表示し、両方の入力欄を空欄にして数字入力を促さなければならない。
- 完了条件：2桁欄と6桁欄の間に固定表示されたハイフンを確認でき、各欄で先頭ゼロを保持して数字を入力できる。OCR候補を反映した場合も、利用者の確認操作なしに自動確定されない。有効候補が0件または複数件の場合は不確かなOCR結果が入力欄へ反映されず、空欄から入力できる。
- 状態：確定
- 備考：画面全体の構成やデザインは未確定とする。

### 5.6 備品番号確定

#### FR-050 備品番号の確定

- 要件：アプリは、利用者の確認を経た前半2桁と後半6桁をASCIIハイフンで連結し、`NN-NNNNNN`形式の文字列として備品番号を確定できなければならない。
- 完了条件：前半が2桁、後半が6桁そろった場合だけ確定でき、利用者の確定操作後に先頭ゼロを保持した備品番号が対象の撮影ジョブへ対応付けられる。
- 状態：確定
- 備考：入力検証は`NN-NNNNNN`形式（正規表現`^[0-9]{2}-[0-9]{6}$`）を前提とし、各数字列の先頭ゼロを保持する。具体的な画面全体やFlutterウィジェットの構成は定めない。

### 5.7 全体写真撮影

#### FR-060 備品全体写真の撮影

- 要件：利用者は、備品番号の確定後に、その備品の全体写真を撮影できなければならない。
- 完了条件：備品番号が確定している撮影手順で全体写真を撮影し、撮影結果を確認できる。
- 状態：確定
- 備考：再撮影時の上書きはFR-072で管理する。

### 5.8 撮影ジョブ管理

#### FR-070 写真と備品番号の一組での管理

- 要件：アプリは、1件の備品について、確定した備品番号、シール写真、および全体写真を1件の撮影ジョブとして管理しなければならない。
- 完了条件：異なる備品の写真が混在せず、対象の備品番号から同じジョブに属する2枚の写真を識別できる。
- 状態：確定
- 備考：備品番号は運用上、一つの備品を一意に識別し、備品番号ごとに有効な完成済み撮影ジョブは1件だけとする。再撮影時の処理はFR-072で管理する。

#### FR-071 撮影ジョブの完成判定

- 要件：アプリは、備品番号が確定し、シール写真、全体写真、および復旧に必要な情報が端末内へ保存された場合に限り、撮影ジョブを完成済みとして扱わなければならない。
- 完了条件：いずれかの条件を満たさないジョブは完成済みまたはアップロード対象として扱われず、すべての条件を満たすジョブだけが完成済みになる。
- 状態：確定
- 備考：未完成ジョブの復旧範囲は未確定とする。

#### FR-072 再撮影時の端末内ジョブ置き換え

- 要件：アプリは、同じ備品番号で新しい撮影ジョブが完成した場合、端末内にある未送信または送信失敗の旧ジョブを新しいジョブで置き換え、備品番号ごとに有効な未送信ジョブを1件だけとしなければならない。新しいジョブが完成するまでは旧ジョブを維持し、再撮影の中断または保存失敗によって旧ジョブを失ってはならない。
- 完了条件：新しいジョブの端末内保存後、新しい2枚の写真が送信対象として有効になり、旧ジョブが有効な未送信ジョブとして併存しない。再撮影を途中で中断または保存に失敗した場合は旧ジョブが維持される。送信済み写真がDriveにある場合は、既存ファイルを変更せず、再撮影した2枚を同名の新規ファイルとして保存できる。
- 状態：確定
- 備考：アプリ内では履歴、別名、別ジョブ、および世代を管理しない。Drive上に過去の同名ファイルが残ることは許容し、その整理はアプリの責務としない。送信競合の実装方式および一部送信成功時の処理は、この要件では定めない。

### 5.9 端末内保存

#### FR-080 アップロード前の端末内保存

- 要件：アプリは、シール写真と全体写真をGoogle Driveへアップロードする前に、キャッシュ領域ではないアプリ専用内部ストレージへ永続保存しなければならない。写真を端末のギャラリーまたは共有メディア領域へ保存してはならない。
- 完了条件：通信できない状態でも完成済みジョブが失われず、アプリ再起動後に未送信ジョブとして確認できる。保存した写真は一般的なギャラリーアプリから閲覧できず、利用者はアプリ内の確認画面で確認できる。
- 状態：確定
- 備考：具体的なFlutter API、パッケージ、ディレクトリ名、ファイルパス、およびローカルジョブ情報の永続化方式は未確定とする。

### 5.10 アップロードキュー

#### FR-090 完成済みジョブのキュー登録

- 要件：アプリは、撮影ジョブが完成して端末内保存に成功した時点ではGoogle Driveへの送信を自動開始せず、完成済みの未送信ジョブをアップロードキューへ登録しなければならない。利用者が「未送信写真を送信」操作を行った時点で、完成済みかつ未送信のジョブを個別選択させずすべて今回の送信対象として確定しなければならない。
- 完了条件：ジョブ完成だけでは送信が開始されず、完成済みジョブがアップロードキューへ登録され、未完成ジョブがキューおよび送信対象に含まれない。「未送信写真を送信」操作時点の完成済み未送信ジョブがすべて今回の送信対象となり、操作後に完成したジョブは開始済みの送信対象へ追加されず次回の送信操作の対象となる。
- 状態：確定
- 備考：同じ備品番号の未送信または送信失敗の旧ジョブは、新しい完成済みジョブで送信対象ごと置き換える。「未送信写真を送信」は確定した操作名だが、配置および画面全体の構成は未確定とする。バックグラウンド送信の要否、送信対象の処理順序、同時実行数、一時停止・取消し、および送信競合の具体的な制御方法は未確定とする。

#### FR-091 オフライン時の未送信データ保持

- 要件：アプリは、オフライン、送信待ち、または送信失敗の場合、未送信ジョブと写真を固定の日数上限を設けず、正常な送信完了まで端末内に保持しなければならない。アプリ終了、端末再起動、端末紛失、担当変更、または時間経過だけを理由に自動削除してはならない。
- 完了条件：送信が正常に完了していないジョブと写真が、時間経過、アプリ終了、端末再起動、またはネットワーク復旧後も送信対象として残り、ネットワーク復旧だけでは送信が開始されず、利用者の「未送信写真を送信」操作によって送信を開始できる。
- 状態：確定
- 備考：オフラインからオンラインへ変化したことだけを契機とした自動送信は行わない。アプリのアンインストール、アプリデータ消去、または端末初期化後の保持は保証せず、端末故障・紛失時のバックアップまたは復元は行わない。利用者が未送信ジョブを手動削除できるかは未確定とする。

#### FR-092 撮影処理とアップロード処理の独立

- 要件：利用者は、撮影済みデータのアップロード完了を待たずに次の備品の撮影へ進めなければならない。
- 完了条件：完成済みジョブが未送信または送信中であっても、アップロード開始または完了を待たずに次の備品についてシール写真の撮影を開始できる。
- 状態：確定
- 備考：アップロード処理の実現方式はこの文書では定めない。

### 5.11 Google認証

#### FR-100 Google Drive利用時の認証

- 要件：利用者本人は、スマートフォン上で本人の業務用Google Workspaceアカウントへサインインしなければならない。アプリはGoogleアカウントへのサインインとGoogle Driveへのアクセス許可を分離して扱い、Drive操作に必要なアクセス許可をOAuth 2.0による認可として必要な操作の段階で取得できなければならない。
- 完了条件：本人の業務用WorkspaceアカウントへのサインインとDriveアクセスの認可を個別に確認でき、必要な認証および認可が成立している場合だけアップロードを実行できる。成立していない場合は送信成功として扱われない。
- 状態：確定
- 備考：アプリはGoogleアカウントのパスワードを保持しない。認証および認可はスマートフォン上で行い、独自の認証バックエンド、サービスアカウント、およびサービスアカウント秘密鍵を使用しない。具体的なOAuthスコープ、認証ライブラリ、API、およびトークンの取得・保存・更新方法は未確定とする。

### 5.12 Google Driveへの保存

#### FR-110 Google Driveへの写真保存

- 要件：アプリは、完成済みジョブに属するシール写真と全体写真をJPEG（MIMEタイプ`image/jpeg`、拡張子`.jpg`）とし、正規形の備品番号を用いた`<備品番号>_label.jpg`と`<備品番号>_overall.jpg`の名前で、所属職員が利用できる既存のGoogle Workspace共有ドライブ内に設けた備品管理用フォルダへ新規ファイルとしてアップロードしなければならない。担当者個人のマイドライブは保存先として使用せず、保存されたファイルは共有ドライブに属するものとする。
- 完了条件：本人の業務用Workspaceアカウントに設定された既存の権限で、対象ジョブの必要な写真が所定の共有ドライブ内フォルダへ保存されたことを確認した後に限り、そのジョブが送信済みになる。書き込めない場合は保存成功として扱わず、利用者へエラーを案内する。
- 状態：確定
- 備考：送信ごとに2枚を新規作成し、同名ファイルが存在しても検索、特定、内容更新、削除、移動、整理、統合、共有設定変更、および権限変更を行わない。撮影日時、内部ID、連番、世代などの識別情報をファイル名へ追加しない。新規アップロードで得たDriveファイルIDを、過去ファイル更新用の対応情報として送信完了後も保持しない。送信競合の制御、および一部の写真だけが保存された場合の扱いは未確定とする。

### 5.13 再送

#### FR-120 送信失敗後の再送

- 要件：アプリは、Google Driveへの送信に失敗したジョブと写真を失わず、再送可能な状態で保持しなければならない。
- 完了条件：送信失敗後も対象ジョブを確認でき、再送の対象にできる。
- 状態：確定

## 6. 異常時・中断時の要件

- ネットワーク切断によって未送信ジョブおよび写真が失われてはならない。

- 一部の写真だけが保存された場合の処理は未確定とする。

### 6.6 カメラまたはOCRの失敗

- カメラによる撮影が完了しなかった場合、その写真を撮影済みとして扱ってはならない。
- OCRで候補を得られなかった場合、利用者が失敗を確認できなければならない。
