# テスト計画書

## 1. 文書情報

- プロジェクト名：asset-photo-manager
- 文書状態：初期版
- 最終更新日：2026-08-31
- 現在のテスト実施状態：未実施

## 2. 目的

この文書は、asset-photo-managerの機能をどの環境と方法で検証するかを定める初期テスト計画である。
テスト対象、環境ごとの役割、異常系、実機確認項目、および完了判定の方針を整理する。

現時点ではFlutterプロジェクトおよびコードが未作成であるため、テストケースの実装と実行は行っていない。

## 3. 対象範囲

次をテスト対象とする。

- 備品シール写真の撮影
- OCRの実行
- 備品番号候補の抽出
- OCR結果の確認と手修正
- 備品番号の確定
- 備品全体写真の撮影
- 撮影ジョブの管理と完成判定
- アップロード前の端末内保存
- 完成済み未送信ジョブの復旧
- アップロードキュー
- オフライン時の保持
- 撮影処理とアップロード処理の独立
- Google認証
- Google Driveへの保存
- 送信失敗後の再送
- 送信状態の保持
- 権限エラーと利用者向け表示
- 認証情報および実データの保護

備品台帳、貸出、返却、棚卸し結果などの業務管理機能、およびGoogle Drive以外の
クラウドサービスは初期開発の対象外であり、この計画のテスト対象に含めない。

## 4. テストの基本方針

- 自動テスト、Androidエミュレーター、Android実機テストの役割を分ける。
- 自動テストだけで実機依存機能を完了扱いにしない。
- 正常系だけでなく、異常系、中断、再起動、再送、および部分的失敗を重視する。
- `docs/requirements.md`に記載された要件の完了条件と対応付けて結果を判定する。
- 未確定仕様に依存するテスト条件を推測で確定しない。
- テストを実行していない項目は「未実施」として扱う。
- 実機テストでは、対象端末、Androidバージョン、アプリ版またはコミットを記録する。
- 特定のテストライブラリ、モックライブラリ、およびCIサービスは、この計画では選定しない。

## 5. テスト環境と役割

### 5.1 区分の意味

機能別テスト方針では、各環境の役割を次の区分で示す。

| 区分 | 意味 |
| --- | --- |
| 主 | その観点を中心的に検証する環境 |
| 補助 | 主となる環境の検証を補う環境 |
| 必須 | 機能の完了判定に欠かせない環境 |
| 対象外 | その環境では検証対象としない |
| 要決定 | 未確定仕様または実装方式の決定後に役割を定める |

「必須」は、他の環境での検証を不要とする意味ではない。

### 5.2 自動テスト

外部機能との境界を分離し、主に次を確認する。

- OCR結果から備品番号候補を抽出するロジック
- 入力確認と手修正に関するロジック
- 撮影ジョブの完成判定
- 送信状態の遷移
- アップロードキューの登録条件
- 永続化対象データの読み書き境界
- エラー処理
- 外部機能を切り離したGoogle Drive連携処理

カメラ、実画像でのOCR、Android権限、実際のGoogle認証、およびGoogle Driveへの実保存は、
自動テストだけで確認済みとしない。

### 5.3 Androidエミュレーター

主に次を確認する。

- 画面遷移
- 入力、確認、および手修正
- 一般的な状態表示とエラー表示
- アプリ終了後の復旧
- ネットワーク状態を変化させた場合の動作
- 対応可能な範囲での権限操作

エミュレーター上のカメラや認証結果だけで、Android実機確認を代替したことにしない。

### 5.4 Android実機

少なくとも次を実機で確認する。

- カメラ撮影
- 実際のシールを模したテスト画像でのOCR
- カメラ権限
- 端末内保存
- アプリ終了後の復旧
- 端末再起動後の完成済み未送信ジョブ復旧
- オフラインからオンラインへ変化した場合の保持と再送
- Google認証
- Google Driveへの保存
- 認証切れや権限不足時の動作
- 連続撮影中にアップロード完了を待たないこと
- 対象Android環境での基本操作

Androidの最低バージョンおよび対象実機は未確定である。

## 8. テストデータ

- 実在する備品番号、実際の備品写真、個人情報、および認証情報をリポジトリへ含めない。
- 架空の備品番号と、テスト専用に作成したシールおよび写真を使用する。
- 架空の備品番号は`NN-NNNNNN`形式とし、数字2桁、ASCIIハイフン、数字6桁であること、および各数字列の先頭ゼロが失われないことを確認する。
- 形式に合わない値を備品番号として確定しないことを確認する。
- 異なる備品に同じ備品番号が割り当てられるケースは、運用上のテスト対象外とする。
- 同じ備品を複数回撮影した場合の期待動作は、Q-009の決定後に具体化する。
- 正常に読み取れる画像に加え、ぼけ、傾き、反射、暗さ、部分欠けを含むテスト画像を用意する方針とする。
- テスト用画像をGit管理するかは、内容、容量、権利、および機密性を確認してから決定する。
- Google認証とDrive連携に使うテストアカウントの運用方法は未確定とする。
- 秘密情報をソースコード、文書、テストコード、ログ、およびGit履歴へ含めない。

## 10. 開始条件と完了条件

### 10.1 テスト実装の開始条件

- 対象要件の期待結果が確定している。
- 対象機能の設計または外部境界が明確になっている。
- 未確定仕様を推測でテストへ固定していない。

### 10.2 自動テスト完了条件

- 対象となる自動テストを実際に実行している。
- 結果が記録されている。
- 失敗や未実施を成功扱いにしていない。

### 10.3 機能のテスト完了条件

- 関連する確定要件の完了条件を確認している。
- 必要な自動テスト、エミュレーター確認、およびAndroid実機確認を実施している。
- 実機依存機能について必要な実機確認が完了している。
- 異常系と復旧を確認している。
- 未解決の重大な問題がない。
- 実施環境と結果が記録されている。

この初期版を作成しただけでは、テスト計画全体または各機能のテストが完了したことにはしない。

## 13. 更新規則

- 要件または設計の変更に応じて更新する。
- 未確定事項が決定したら、対応するテスト条件と期待結果を具体化する。
- 実装方式だけを理由に、要件上必要な実機確認を削除しない。
- 実施していないテストを成功扱いにしない。
- テスト結果の細かな履歴とテスト計画を混在させない。
- 不要になった方針は理由なく削除せず、関連する`docs/decisions.md`の判断記録と整合させる。
